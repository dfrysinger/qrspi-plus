The new `reviewer_tag` charset rule `^[a-z0-9-]+$` — added in both `first-party-emission.md:70` and `third-party-emission.md:49` as the R3 close of R2 F03 / sec-codex R2 F01 — is correctly stated as a literal regex but is **too permissive** in one dimension that matters for the threat model it is supposed to close: it admits tags whose first character is `-` (e.g. `-rf`, `-evil`, `--help`, or even the single character `-`). Path construction then yields filenames like `<round_subdir>/-rf.finding-F01.md` and `<round_subdir>/-evil.clean.md`. Leading-hyphen filenames are a well-known POSIX argument-parsing footgun: downstream tools that consume the round-subdir via shell glob expansion (`for f in round-01/*.finding-*.md; do tool "$f"; done`, `cat round-01/*`, `grep ... round-01/*`) and pass the path without a `--` end-of-options separator will interpret the leading `-` as a CLI flag. The pre-fix attack surface (path-traversal or shell-metachar reviewer tags) was correctly closed by the charset class; the leading-hyphen sub-case is the residual.

This matters specifically because of the third-party threat model the round-3 fix package explicitly acknowledges. The `reviewer:` audit field that ends up driving the splitter's filename derivation comes from Codex stdout inside a prompt-injectable sandbox — that is exactly why the regex was introduced (`third-party-emission.md:49`: "A boundary block carrying a reviewer_tag that fails the regex is malformed and produces zero finding files for that tag"). The R3 NO_FINDINGS iron-law addition at `third-party-emission.md:80` shows the team agrees the Codex stdout channel is adversarial. An attacker who lands a prompt injection in the wrapped artifact body need only get Codex to emit `reviewer: -rf` (or any leading-hyphen value) in a `<<<FINDING-BOUNDARY>>>` frontmatter block; that value passes the regex, the splitter materializes `<round_subdir>/-rf.finding-F01.md`, and any orchestrator step that subsequently iterates the round directory with a naive glob inherits the argument-parsing ambiguity.

Concrete attack scenario: a `feedback/*.md` file (or any wrapped artifact) crafted by a future contributor contains a prompt-injection payload instructing the Codex reviewer to emit a finding with `reviewer: --output=/tmp/pwned` in its YAML frontmatter. The regex accepts this string (only lowercase letters, digits, and hyphens). The splitter writes `<round_subdir>/--output=/tmp/pwned.finding-F01.md`. The apply-fix step-2 schema-violation guard, or the Haiku-verifier dispatcher, then enumerates findings and passes the path to a CLI tool (Haiku invocation, scope-tagger, dispositions writer, or even a simple `cat` for diagnostic). The leading `--` is consumed as an option terminator-or-flag, breaking the call or, worse, redirecting tool behavior. Equality is harder than usual to assert because the splitter side never sees the dispatcher-supplied `reviewer_tag` parameter compared against the YAML field — the contract is silent on whether the splitter validates `reviewer:` against the dispatcher param OR derives the filename from the dispatcher param OR trusts the YAML field, so the regex check is doing the load-bearing safety work on its own.

Fix: tighten the regex to require an alphanumeric first character — `^[a-z0-9][a-z0-9-]*$` — in both `first-party-emission.md:70` and `third-party-emission.md:49`, and update the assertion in `tests/unit/test-per-finding-file-emission.bats:L224-L227` to pin the tightened pattern. Every dispatcher-supplied tag in the Expected-Reviewer Matrix (`skills/reviewer-protocol/SKILL.md:L23-L36`) — `quality-claude`, `scope-claude`, `quality-codex`, `scope-codex`, `spec-claude`, `security-claude`, `goal-traceability-claude`, `test-coverage-claude`, `silent-failure-claude`, `code-quality-claude`, `implement-gate-claude`, `integration-claude`, and their `-codex` siblings — starts with `[a-z]` and so passes the tightened regex. Optional belt-and-suspenders: also forbid trailing hyphen (`^[a-z0-9]([a-z0-9-]*[a-z0-9])?$`) since none of the canonical tags end in `-` either; this guards against splitter output where a trailing-hyphen tag would produce ambiguous boundary filenames if a future caller appends a suffix. The minimum acceptable fix is the leading-hyphen guard; the trailing-hyphen guard is nice-to-have.
